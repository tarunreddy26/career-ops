# Operations Analytics Dashboard — Project Notes

My own explanation of how this project works, end to end, in plain language.

---

## 1. What this project is

It takes raw operations data (work orders moving through a fulfillment/manufacturing
process), cleans it, stores it in a SQL database, calculates the metrics that matter
for running an operation, and shows them on a dashboard. The whole thing runs from a
single command and produces the same result every time, so "refreshing" the data is
just re-running it.

The three metrics the whole project is built around:
- **Throughput** — how much work gets finished per day.
- **Cycle time** — how long each order takes to process.
- **Cost** — how much it costs to produce the output.

## 2. The flow (the big picture)

```
Raw dataset (CSV)
   → load it untouched into SQL          (staging)
   → clean + transform it with Pandas    (Python)
   → reshape into a star schema in SQL    (fact + dimension tables)
   → build KPI views in SQL
   → show it on a dashboard
```

This is a classic data pipeline. Because the raw data is loaded into SQL *first* and
transformed *afterward*, it leans toward **ELT** (Extract, Load, Transform) rather than
old-style ETL where you transform before loading. The important idea either way: keep
the original raw data, then build cleaned layers on top of it.

## 3. The data

The dataset is one row per **work order**. Each order has:
- IDs and labels: `order_id`, `product_id`, `product_name`, `product_category`,
  `region`, `facility`, `priority`.
- Quantities: `units`.
- Timestamps: `created_at` (order placed), `started_at` (processing began),
  `completed_at` (processing finished — empty if still in progress or cancelled).
- Status: `completed`, `in_progress`, or `cancelled`.
- Costs: `unit_cost`, `labor_cost`, `shipping_cost`.

The data is **simulated** (generated by code) on purpose, so the project runs anywhere
without downloading anything. The generator deliberately adds realistic "mess" so the
cleaning step has real work to do:
- some orders have no completion time (still running or cancelled),
- the category text is inconsistent (different capitalization, extra spaces),
- a few rows are exact duplicates,
- a few cost values are negative or zero (data-entry style errors),
- a small number of orders have unusually long processing times (stuck orders).

To use a real public dataset instead, I'd drop a CSV into `data/raw/` and adjust the
column mapping. A good real fit is the Olist e-commerce dataset, which has order
timestamps (for cycle/lead time) and price + freight (for cost).

## 4. The three KPIs, defined precisely

### Throughput
The number of orders (and units) **completed** per day. It's a `COUNT` of finished
orders grouped by date. Key point: it counts things that *finished*, not things that
arrived. Arrivals are demand; throughput is output.

### Cycle time
The time from when processing **started** to when it **finished**:
`cycle_time = completed_at − started_at`, measured in hours.

Important detail: cycle time is **right-skewed** — most orders are quick, but a few
slow ones drag the average up. So I report the **median** and the **P90** (the value
90% of orders come in under), not just the mean. The median tells the typical story;
the P90 shows the bad tail.

Related but different metric: **lead time** = `completed_at − created_at` — the *total*
time the order sat in the system, including the wait before processing started. Cycle
time is the active work; lead time is the whole journey.

### Cost
Total cost of an order = `units × unit_cost + labor_cost + shipping_cost`. I also track
**cost per unit** (total cost ÷ units), which is the efficiency number — it lets me
compare across products and months fairly.

These three are intentionally in tension: I can push throughput up by spending more, or
cut cost by slowing down. Looking at all three together stops me from improving one
while quietly wrecking another.

## 5. Walking through each file

### `src/generate_data.py` — get the raw data (Extract)
Creates the raw dataset and writes it to `data/raw/operations_raw.csv`. Uses a fixed
random seed so it produces the exact same 25,000+ rows every run (reproducible). This
is the only step that's "fake" — in a real project this would instead download or pull
from a source system.

### `src/extract_load.py` — load raw into SQL (Load)
Reads the raw CSV and writes it, completely untouched, into a SQLite table called
`stg_orders_raw` ("stg" = staging). It reads every column as text so nothing gets
silently changed on the way in. Loading raw-first means I always have an exact copy of
the source, and I can re-run the transforms without re-fetching the data.

### `src/transform.py` — clean and reshape (Transform + Model)
This is the core. It reads the raw staging table and does the real work:

1. **Remove duplicates** — drop exact duplicate rows.
2. **Fix data types** — convert the timestamp columns to real datetimes and the cost
   columns to numbers. Bad values become "missing" instead of crashing the script.
3. **Standardize text** — trim spaces and fix the capitalization on the category field
   so "WIDGETS", "widgets", and " Widgets " all become "Widgets".
4. **Fix cost errors** — turn negative labor costs into positive (took absolute value),
   and replace zero unit-costs with the typical (median) cost for that product.
5. **Derive the metrics** — calculate `cycle_time_h`, `lead_time_h`, and `total_cost`
   for every order.
6. **Sanity-guard** — if an order somehow "finished before it started," null out its
   cycle time instead of keeping a negative number.
7. **Flag completed orders** — a true/false `is_completed` column, because the
   throughput and cycle-time KPIs only count finished orders.

Then it reshapes the clean data into a **star schema** (explained below) and writes the
tables back into SQL, adding indexes so lookups by date/region/product are fast. It
also prints a small report of everything it cleaned, so the process is auditable — I
can see exactly how many rows were dropped or fixed.

### `sql/kpi_views.sql` — the KPI definitions in SQL
Creates SQL **views** (saved queries) that define each KPI once, in one place:
- `v_throughput_daily` — completed orders/units per day.
- `v_cycle_time_monthly` — average/min/max cycle time per month and region.
- `v_cost_monthly` — total cost and cost-per-unit per month and category.
- `v_kpi_scorecard` — a single-row summary of all the headline numbers.

Putting KPI logic in views means the dashboard just reads these — it doesn't re-invent
the math. One source of truth.

### `src/build_dashboard.py` — the dashboard (Serve)
Reads the KPI views and builds an interactive HTML dashboard (`output/dashboard.html`)
with:
- a row of **KPI cards** at the top (orders completed, units, average & median & P90
  cycle time, total cost, cost per unit),
- a **throughput** line chart (daily + a 7-day smoothed average),
- a **cycle-time** chart showing median vs P90 per month,
- a **cost-per-unit** chart broken down by product category,
- a **histogram** showing the spread of cycle times.

(The median and P90 are calculated here in Python because SQLite doesn't have a
built-in percentile function.)

### `src/run_pipeline.py` — run everything (Orchestrator)
The single entry point. It runs the steps in order — generate (if needed) → load →
transform → build views → build dashboard — and times the whole thing. Running it again
rebuilds everything from scratch identically. **This is the "repeatable refresh":** one
command, same result every time.

### `powerbi/` — the Power BI version
- `MEASURES.dax` — the same KPIs written as Power BI **DAX measures** (throughput,
  median/P90 cycle time, total cost, cost per unit, month-over-month change).
- `POWERBI_SETUP.md` — step-by-step instructions to connect Power BI to the SQL
  database, set up the table relationships, and build the same visuals.

The Plotly dashboard and the Power BI build show the *same* numbers because both read
the same SQL tables and views.

## 6. The star schema (data modeling)

After cleaning, the data is split into one **fact** table and several **dimension**
tables — this shape is called a *star schema*.

- **Fact table (`fact_orders`)** — the measurements. **Grain = one row per work order.**
  ("Grain" just means what a single row represents — this is the most important thing to
  be able to state about any table.) It holds the numbers (units, costs, cycle time,
  total cost) plus keys that link out to the dimensions.

- **Dimension tables** — the descriptive context I slice by:
  - `dim_date` — calendar info (year, quarter, month, weekday) for each date.
  - `dim_product` — product name and category.
  - `dim_region` — the regions.
  - `dim_facility` — facilities and which region they belong to.

Why do it this way: the facts (things you measure) are separated from the dimensions
(things you group/filter by). It avoids repeating text everywhere, keeps the data clean,
and it's exactly the shape Power BI and other BI tools expect — so building visuals and
"slice by region / product / month" filters becomes trivial.

## 7. Why SQL *and* Python/Pandas (instead of just one)

- **SQL** is the durable store and single source of truth. It holds the raw data and
  the cleaned tables, handles data bigger than memory, and the dashboard connects
  straight to it. It's also better for set-based joins and aggregations.
- **Pandas** is where flexible, row-by-row cleaning and metric derivation happen — fixing
  types, handling missing values, calculating cycle time. That's awkward in pure SQL but
  natural in Python.

So each tool is used for what it's best at: Python for messy transformation, SQL for
storage and aggregation.

## 8. "Repeatable refresh" — what it actually means

The pipeline is **idempotent**: running it again gives the same result, with no manual
steps. When new data arrives, I just re-run `run_pipeline.py` and the dashboard updates.

- For this project, every refresh reloads everything (a **full refresh**) — fine because
  the dataset is small.
- For large/production data, the better approach is an **incremental refresh**: only pull
  rows newer than the last load, instead of reloading everything. And a scheduler (cron,
  or a Power BI Gateway for scheduled refresh) would run it automatically on a schedule.

## 9. Tech choices, summarized

| Choice | Why |
|--------|-----|
| **SQLite** as the database | Zero setup, real SQL, works anywhere; easy to swap for PostgreSQL/SQL Server later |
| **Pandas** for transforms | Best tool for cleaning messy data and deriving row-level metrics |
| **Star schema** | Clean separation of measures vs. context; the shape BI tools want |
| **SQL views** for KPIs | KPI logic defined once, reused by every consumer |
| **Median + P90** for cycle time | Honest for a skewed metric; the mean alone hides the slow tail |
| **One orchestrator script** | Makes the refresh a single, reproducible command |

## 10. The numbers from the last run

- ~25,120 raw rows → 25,001 after cleaning → 23,917 completed orders.
- 119 duplicates removed, 40 negative costs corrected, 40 zero costs imputed.
- Star schema built: `fact_orders` (25,001 rows) + 4 dimension tables.
- Full refresh completed in about 4 seconds.

## 11. Things I'd improve next

- Swap the simulated data for a real public dataset.
- Move to PostgreSQL for a more production-like database.
- Add automated data-quality checks (row counts, null thresholds) that fail loudly.
- Switch to incremental refresh and schedule it.
- Add alerting when a KPI crosses a threshold (e.g., cycle time spikes).
